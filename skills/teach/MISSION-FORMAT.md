# Formato de MISSION.md

`MISSION.md` vive en la raíz del workspace. Captura la _razón_ por la que el usuario está aprendiendo este tema. Toda decisión de enseñanza —qué enseñar a continuación, qué recursos sacar a la luz, qué ejercicios diseñar— debe poder rastrearse hasta este documento.

## Plantilla

```md
# Misión: {Tema}

## Por qué
{1-3 frases. El objetivo concreto del mundo real que persigue el usuario. ¿Qué cambia en su vida o su trabajo cuando tenga esta habilidad? Evita formulaciones abstractas como "entender X": empuja hacia el resultado subyacente.}

## El éxito se ve así
- {Algo específico y observable que el usuario será capaz de hacer}
- {Otra cosa específica}
- {…}

## Restricciones
- {Tiempo, presupuesto, compromisos previos, preferencias de aprendizaje, cualquier cosa que acote el enfoque}

## Fuera de alcance
- {Temas adyacentes que el usuario explícitamente no quiere perseguir ahora; protege la zona de desarrollo próximo}
```

## Reglas

- **Una misión por workspace.** Si el usuario quiere aprender dos cosas no relacionadas, son dos workspaces.
- **Concreto antes que abstracto.** "Correr una media maratón en octubre" supera a "ponerme en forma". "Entregar una CLI en Rust a mi equipo" supera a "aprender Rust".
- **Insiste ante la vaguedad.** Si el usuario no sabe articular el porqué, entrevístalo antes de escribir nada. Una mala misión es peor que ninguna misión.
- **Revisa cuando la realidad cambie.** Las misiones cambian. Cuando el objetivo del usuario se mueva, actualiza este archivo; no dejes una misión obsoleta dirigiendo futuras sesiones.
- **Hazlo corto.** Si `MISSION.md` se pasa de una pantalla, ha dejado de ser una brújula y ha empezado a ser un plan.
