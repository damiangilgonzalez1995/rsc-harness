1. La idea en tres líneas

Un hook en Claude Code es un comando de terminal que Claude Code ejecuta solo cuando ocurre un evento: se abre la sesión, el usuario envía un mensaje, se va a ejecutar una herramienta, se cierra la sesión.

Lo que ese comando imprime por pantalla se añade al contexto del modelo como si fuera una instrucción más. Así es como el harness "habla" con Claude sin tocar el CLAUDE.md.

rsc instala scripts de Node en .rsc/ y los registra en los settings. Ningún script llama a una IA. Son reglas fijas: si existe tal fichero, imprime tal texto.

2. Dónde está cableado

Hay dos ficheros de settings, y esto despista. Cada uno registra hooks distintos.

.claude/settings.json

Se comparte con el equipo (va en git). Registra 3 hooks: SessionStart, PreCompact, SessionEnd. Son los que inyectan texto.

.claude/settings.local.json

Solo tu máquina (no va en git). Registra 7 hooks de memoria de sesión, todos al mismo script con un argumento distinto. Son silenciosos: escriben un diario local.

Los scripts a los que apuntan viven en .rsc/ dentro de tu proyecto. Son copias; el paquete npm ya no hace falta para que funcionen.

.rsc/
  session-start.mjs            ← hook 1 (279 líneas)
  suggest-always-on.md         ← el texto que inyecta el hook 1
  worklog-checkpoint.mjs       ← hook 2 (26 líneas)
  session-memory-adapter.mjs   ← hook 3, punto de entrada (131 líneas)
  session-memory-core.mjs      ← hook 3, la lógica del diario (477 líneas)

  memory/                      ← aquí se escribirá el diario (aún no existe)
  backups/                     ← copias de seguridad de cada instalación

3. El ciclo de vida de una sesión

Orden real en el que Claude Code dispara los hooks de este proyecto. Los dos settings se fusionan: en un mismo evento corren los hooks de ambos.

  • SessionStartAbres Claude Code. Corren session-start.mjs inyecta y session-memory-adapter.mjs claude start inyecta solo si hay checkpoint previo.
  • UserPromptSubmitEnvías un mensaje. Corre adapter claude request silencioso. Anota que hubo actividad.
  • PostToolUse (Edit|Write|NotebookEdit)Claude edita un fichero. Corre adapter claude edit silencioso. Suma 1 al contador de ediciones.
  • PostToolUse (Bash)Claude ejecuta un comando. Corre adapter claude boundary silencioso. Refresca la foto de git (un commit es una "frontera").
  • StopClaude termina su respuesta. Corre adapter claude turn silencioso. Guarda el checkpoint si hubo trabajo.
  • PreCompactEl contexto se va a resumir. Corren worklog-checkpoint.mjs inyecta y adapter claude compact silencioso.
  • SessionEndCierras. Corren worklog-checkpoint.mjs inyecta y adapter claude end silencioso. Marca la sesión como completada.
Lo que NO tienes. En proyectos grandes rsc añade también PreToolUse con tres guardas (danger-guard, gitmoji-guard, ship-guard) y un UserPromptSubmit que reafirma la regla "spec antes de código". En tu plan quedaron diferidos porque dijiste proyecto pequeño. Por eso no ves `.mjs` de guardas en tu `.rsc/`.

4. Hook 1: session-start.mjs inyecta

Comando registrado en settings.json:

node ".rsc/session-start.mjs" ".rsc/suggest-always-on.md" "<raíz del proyecto>"

Recibe dos argumentos: el fichero Markdown a inyectar y la raíz. Luego hace una cadena de diez comprobaciones, cada una con su condición y su bloque de texto. Solo imprime los que aplican.

4.1 El cuerpo siempre activo

Lee .rsc/suggest-always-on.md y lo imprime tal cual. Son tres líneas. Este es el texto que hace que Claude vaya a buscar el perfil de usuario:

# rsc-suggest — always-on operations layer

Read `docs/wiki/harness/user-profile.md` before acting. Use `orient` to keep the user situated and `suggest` to offer a missing skill only when the current task needs it. Close with the configured orientation block.

Antes de imprimirlo pasa por hook-once.mjs: si rsc está cableado a la vez en tu home y en el proyecto, ambos hooks correrían y el texto entraría dos veces. Usa el session_id que Claude Code pasa por stdin como llave y escribe un marcador en la carpeta temporal del sistema. El primero que llega imprime; el segundo calla. Si algo falla, imprime igualmente (fail-open).

4.2 Cómo está escrito cada aviso: el patrón

Los nueve avisos siguen el mismo esqueleto: un if con condiciones sobre ficheros del disco, y un process.stdout.write con el texto. Lo que el script imprime, Claude Code lo pega en el contexto. Ejemplo real, el aviso de auditoría, tal cual está en .rsc/session-start.mjs:

// línea 13: la constante
const STALE_AUDIT_DAYS = 14;

// líneas 39-43: la pregunta "¿toca auditar?"
function auditDue() {
  try {
    const { lastRun } = JSON.parse(readFileSync(join(root, '.rsc', 'audit.json'), 'utf8'));
    return (Date.now() - new Date(lastRun).getTime()) / 86400000 >= STALE_AUDIT_DAYS;
  } catch { return true; }   // no existe audit.json → nunca se auditó → toca
}

// líneas 180-187: la inserción
if (profileExists && auditDue() && !has('.rsc', '.no-audit')) {
  process.stdout.write(`
===== rsc skill audit =====
A skill audit is due (runs at most every ${STALE_AUDIT_DAYS} days). It flags overlapping
skills and skills with no footprint in this project.
ACTION: run \`npx @damiangilgonzalez/harness audit\`. Opt out with .rsc/.no-audit.
===========================
`);
}

Tres condiciones en el if: hay perfil, han pasado 14 días desde la fecha guardada en .rsc/audit.json (o el fichero no existe), y no existe el fichero de apagado. Si las tres se cumplen, se imprime. Ejecutar rsc audit escribe la fecha de hoy en audit.json y el aviso calla otros 14 días.

5. Hook 2: worklog-checkpoint.mjs inyecta

Comando registrado en PreCompact y SessionEnd:

node ".rsc/worklog-checkpoint.mjs" "<raíz del proyecto>"

Una sola condición: si no existe docs/wiki/, no imprime nada. Si existe, imprime siempre este texto:

===== rsc worklog checkpoint =====
If this session did meaningful work (files changed, a decision made, a commit),
run a WORKLOG SWEEP before context is lost:
  1. Write docs/raw/worklog/<YYYY-MM-DD>-<slug>.md using the harness
     wiki-worklog-template.md (what we did · why · files touched · outcome · next).
  2. Compile it into wiki/ (update existing articles first; wikilinks + Related);
     append significant decisions to docs/wiki/harness/decisions.md.
Skip entirely if this was a pure read/answer turn with no changes.
==================================

El hook solo recuerda. Quien escribe el worklog es el agente, y solo si hubo cambios. La plantilla está en .claude/skills/harness/references/wiki-worklog-template.md.

6. Hook 3: session-memory-adapter.mjs silencioso

Un solo script, siete cableados en settings.local.json, cada uno con un evento como argumento:

node ".rsc/session-memory-adapter.mjs" claude start      ← SessionStart
node ".rsc/session-memory-adapter.mjs" claude request    ← UserPromptSubmit
node ".rsc/session-memory-adapter.mjs" claude edit       ← PostToolUse Edit|Write|NotebookEdit
node ".rsc/session-memory-adapter.mjs" claude boundary   ← PostToolUse Bash
node ".rsc/session-memory-adapter.mjs" claude turn       ← Stop
node ".rsc/session-memory-adapter.mjs" claude compact    ← PreCompact
node ".rsc/session-memory-adapter.mjs" claude end        ← SessionEnd

Cada uno tiene un timeout de 5 segundos. El adaptador lee el JSON que Claude Code le pasa por stdin (session_id, evento, cwd), sube por las carpetas hasta encontrar .rsc.json para saber cuál es el proyecto, y llama a session-memory-core.mjs.

6.1 Qué guarda

Solo metadatos de git, nunca contenido:

  • Rama, worktree, HEAD actual y HEAD de referencia al empezar la sesión.
  • Rutas de ficheros modificados y una huella (hash) de cada uno, para saber si cambiaron.
  • Lista de commits hechos durante la sesión.
  • Contador de ediciones y marcas de tiempo.

Lo escribe en .rsc/memory/anchors/claude--<session>.json (la foto inicial) y .rsc/memory/sessions/claude--<session>.json (el estado). Retención 30 días. Esa carpeta está excluida de git.

6.2 Por qué hoy no hay nada

El core tiene una regla: si no hubo trabajo, no escribe registro. Trabajo significa una edición, un fichero nuevo sucio, un fichero que cambió de huella, o un commit. Tu sesión fue de solo lectura, así que .rsc/memory/ ni siquiera se ha creado. Lo confirmé ejecutando el adaptador: devuelve record: null.

6.3 Aviso: en Windows los hooks de memoria no se ejecutan

Comprobado el 8 de septiembre lanzando el adaptador tal como lo lanza Claude Code: no escribe nada. La última línea del script decide si ejecutar el bloque principal comparando import.meta.url con file:// más la ruta del argumento. En Windows uno es file:///C:/Users/... y el otro C:\Users\..., nunca coinciden, y el bloque no corre. En Mac y Linux funciona. Llamando a la función handleLifecycle directamente, el diario se escribe bien; es solo el arranque por línea de comandos lo que falla. Los comandos manuales (/save-session, rsc memory save) sí funcionan porque no pasan por esa línea.

6.4 El único momento en que inyecta

En start, si existe un registro de la misma rama y worktree, lo devuelve a Claude Code como additionalContext. Tiene este formato (máximo 4.096 bytes):

rsc memory: continuation for this branch and worktree
branch: main
worktree: C:\...\prompt-injection-patterns
head: <sha>
changed: blueprint/patterns/dual_llm.py, tests/test_dual_llm.py
commits: 2 since baseline
completed: 2026-09-07T18:02:11Z

Si el registro es de otra rama pero mismo worktree, lo etiqueta como "nearby" y le dice al agente que no lo mezcle en silencio.

7. Por qué el agente lee user-profile.md

Para seguir esta cadena hay que saber cómo carga Claude Code las skills:

  1. Al arrancar, Claude Code escanea .claude/skills/ y de cada SKILL.md lee solo la cabecera: name y description. Mete esas descripciones en el contexto como catálogo. Son los 3,3 KB de "descripciones de skills" que reporta doctor. El cuerpo completo aún no está cargado.
  2. El hook 1 inyecta "Read docs/wiki/harness/user-profile.md before acting. Use orient...".
  3. Claude carga el cuerpo de orient usando la herramienta Skill, porque el hook se lo pide y la descripción dice "Always-on". Ahí lee la regla: "No turn ends in seco" y el bloque de cuatro intenciones:
📍 Dónde estás — the project phase/state (the map)
✅ Qué acabas de hacer — one line, in the user's language
🧭 Por qué — the technical why, scaled to the dial
➡️ Siguiente — 1-3 concrete options, ending in a question
  1. El SKILL.md apunta a references/orientation-contract.md (línea 63) para el detalle: qué significa cada nivel L0 a L3 y cómo combinarlo con el nivel técnico. Claude lo lee si necesita el detalle.
  2. Claude lee tu perfil, ve accompaniment: L0 y technical_level: non-technical, y aplica L0 ("cavernícola"): solo ✅ y ➡️, una opción, pregunta de sí o no.

Las cuatro líneas son intenciones, no texto fijo: Claude las redacta cada vez en tu idioma. Lo que no cambia es el orden ni que la última sea una pregunta. Ejemplo de cierre en L0: "✅ He leído el repo. ➡️ ¿Empiezo por los notebooks?"

El perfil lo escribió onboard con tus respuestas. Edítalo a mano, cambia L0 por L2, y verás cambiar el tono al instante sin tocar código.

8. Los cuatro slash commands los lanzas tú

Cada fichero de .claude/commands/ es un prompt. Escribes /nombre, Claude recibe el texto, y él ejecuta el comando rsc que se le indica.

CommandTexto que recibe ClaudeComando rsc que acaba ejecutando
/save-session"Invoke memory:save with the current local session identifiers. Persist only allowed git and SDD ledger metadata; never include conversation or file content."rsc memory save --session <id>
/resume-session"Invoke memory:resume for the current branch and worktree. Label a nearby branch result as nearby; never merge it silently."rsc memory resume
/learn "texto""Invoke memory:learn for exactly one proposed lesson. After individual explicit approval, run rsc memory learn... Without that approval, write nothing."rsc memory learn --text ... --approve
/checkpoint"Run sello freeze, complete the required review, then run sello approve only with the observed lenses. Do not treat freeze as approval."rsc sello freeze / approve

/checkpoint pertenece al sistema "sello", que en tu proyecto está desactivado (rsc doctor lo reporta como enabled: false). Está instalado porque el comando existe en el catálogo, pero no hará nada útil hasta activar sello.

9. rsc doctor y rsc repair

rsc doctor: diagnostica, no toca nada

Compara lo que .rsc.json declara con lo que hay en disco. Comprueba que cada hook registrado apunta a un fichero que existe (un clon fresco trae settings.json pero no .rsc/, y sin este chequeo parecería sano). Lista skills instaladas y faltantes, comandos sin respaldo, backups, estado de sello, modo de memoria, y un presupuesto de contexto: cuántos KB entran por sesión y por turno.

rsc repair: arregla, con una frontera clara

Cada hallazgo nace clasificado como restore o change. Restore es devolver el harness a lo ya declarado: un enlace roto, un hook duplicado, una carpeta de un layout viejo. Eso lo hace solo, tras crear un backup. Change es alterar una decisión: cambiar de asistente, adoptar una skill que añadió un compañero, desarmar una guarda. Eso lo pregunta uno a uno.

Salida de rsc doctor en tu proyecto hoy: 9 skills instaladas, 0 faltantes, hooks cableados, 4 backups, sello desactivado, memoria en modo full y lista. Presupuesto: 6,9 KB por arranque, 0 KB por turno, 3,3 KB de descripciones de skills siempre en contexto.

El hook 1 tiene una sección "un harness roto se arregla solo": si Claude detecta síntomas (no ve skills, un hook se repite, .rsc.json no cuadra), debe ejecutar doctor, describir el síntoma en una línea y ofrecer repair una sola vez por sesión.

10. Lo que añade un proyecto grande

Tu plan dejó varias piezas diferidas por ser un proyecto pequeño. Con un plan mediano o grande, el mismo targets/claude.js cablea además estos hooks. La diferencia clave: no imprimen avisos, bloquean. Devuelven una decisión deny por stdout y Claude Code cancela el comando antes de ejecutarlo.

ScriptEventoQué hace
danger-guard.mjsPreToolUse (Bash)Lee el comando que Claude va a ejecutar. Si es irreversible (rm -rf, git push --force, git reset --hard, git clean...), responde deny con el motivo. Claude ve el rechazo y tiene que pedirte permiso.
gitmoji-guard.mjsPreToolUse (Bash)Si el comando es git commit y el mensaje no empieza por un emoji de la convención gitmoji, lo rechaza.
ship-guard.mjsPreToolUse (Bash)Impide cambiar a main o mergear a main fuera del flujo ship. Con sello.mjs activado, además exige que los bytes que se commitean sean exactamente los que se revisaron: un "sello" firma el contenido revisado y el guard compara.
userprompt-gate.mjsUserPromptSubmitEn cada mensaje tuyo reinyecta la regla "una feature nueva pasa por grill-with-docs y to-spec antes de escribir código". Se inyecta en cada turno porque en sesiones largas la instrucción del arranque queda lejos y el modelo la olvida.

Además instala cuatro agentes base en .claude/agents/ (revisor, depurador, resolutor de builds, planificador) y un revisor específico por stack. Se activan cuando el proyecto desarrolla la necesidad: rsc reassess comprueba la evidencia y propone un plan nuevo que tú tienes que aceptar.
